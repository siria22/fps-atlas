# 데이터 작업 흐름 (로컬 전용)

DB가 기준이다. `data/`의 두 파일은 "DB 사본 + 이번에 고칠 내용"을 담는 작업용 사본이고, 반영할 때마다 DB에서 다시 뽑는다.
키(서비스 키·관리 API 토큰)는 이 저장소의 `.env`에만 있고 스크립트가 직접 읽는다. 어시스턴트는 명령만 실행한다.

```
data/                    (git 추적 안 함)
├─ atlas.json            게임 → 맵 → 맵↔장소 연결(근거 수준·출처·설명·스크린샷), 장소는 맨 위에 한 번만
├─ names.json            게임·맵의 언어별 검색 별칭 (DB game_aliases·map_aliases, lang 칸)
├─ .research/            이름 조사 입력·결과(조사할 때만)
└─ .review/              검수하는 동안만 (반영이 끝나면 지워짐)
   ├─ base.json          뽑았을 때의 원본 사본(비교 기준)
   ├─ worklist.json      작업 목록: 처리할 제보·수정 제안(출처 번호), 요청 내용·이유·어시스턴트 메모·할 일
   ├─ images/            제보 이미지 썸네일(검수기에서 보기용)
   ├─ diff.json          파일 대 DB의 차이(바뀐 행만 DB에서 새로 읽음)
   ├─ decisions.json     검수기에서 고른 결과
   └─ apply.sql          반영할 때 실행한 SQL
└─ .history/             반영할 때마다 남기는 작업 로그·백업(지우지 않고 쌓임)
   ├─ <YYYYMMDD-HHMMSS>/ apply.sql · decisions.json · worklist.json · db-before.json(반영 전 DB 사본) · summary.txt
   └─ discarded.log      pull --force로 버린 작업 한 줄씩(시각, 상태, 버린 행 수, 작업 목록 항목)
```

## 작업은 한 번에 하나, 깨끗한 상태에서 시작

- 작업 종류: **직접 수정**(검수기 탭 1, `import-names`) 또는 **제보 처리**(`inbox` → 작업 목록).
- 깨끗함 = 작업 파일이 `.review/base.json`(뽑았을 때의 DB)과 같음. `status`가 깨끗함 / 직접 수정 중 / 제보 처리 중을 알려 준다.
- `inbox`는 깨끗할 때(또는 이미 제보 처리 중일 때)만 된다. 직접 수정이 남아 있으면 먼저 반영하거나 버린다.
- `import-names`는 제보 처리 중에는 안 된다. 탭 1 수정은 제보 처리 중에도 된다(어시스턴트가 채운 것을 손질). 작업 목록과 관계없는 행을 고치면 `diff`가 경고한다.
- `pull`은 고친 내용이 남아 있으면 멈춘다. `--force`만 버린다(버리는 행 수를 출력).
- 검수기 탭 1은 고칠 때마다 `atlas.json`에 바로 저장한다(브라우저에 남기지 않음). 그 사이 파일이 밖에서 바뀌었으면 덮어쓰지 않고 멈춘다 → "파일 다시 읽기".

## 명령

| 명령 | 하는 일 |
|---|---|
| `npm run atlas -- status` | DB의 '검토 대기' 제보·수정 제안 수, 지금 작업 상태 |
| `npm run atlas -- pull [--force]` | DB 전체 → `atlas.json`·`names.json` + `.review/base.json`. 검수 중인 작업이 있으면 멈춤(`--force`는 버림) |
| `npm run atlas -- inbox` | '검토 대기' 제보·수정 제안 → 작업 목록. 구조화된 칸은 `atlas.json`에 바로 반영, 나머지는 항목의 `todo` |
| `npm run atlas -- import-names [폴더]` | 이름 조사 결과(기본 `data/.research/out`) → `names.json` |
| `npm run atlas -- diff` | 차이 → `.review/diff.json` (검수기 탭 2가 읽음) |
| `npm run atlas -- apply [--dry-run]` | 고른 것만 DB에 반영 → `.history/<시각>/`에 로그·백업 보관 → `.review/` 지우고 다시 pull. `--dry-run`은 SQL만 만들고 보관하지 않음 |

검수기: `scripts/seed/seed-review.html` 탭 2 → **data 폴더 열기**(`E:\projects\Web\FpsViewer\data`).

## 제보 처리 — 작업 목록이 어떻게 동작하나

순서는 `status` → `pull` → `inbox` → (작업 목록 채우기) → `diff` → 검수기 탭 2 → `apply --dry-run` → `apply`.
**언제 돌릴지, 각 항목을 어떻게 판단할지, 무엇을 보고할지는 PersonalAssistant의 서비스 관리 스킬이 정한다.** 이 문서는 도구가 무엇을 만들고 무엇을 받아들이는지만 적는다(판단 규칙을 여기에 쓰지 않는다).

`inbox`가 만드는 것:
- 제보마다 새 장소 자리 `new-<제보 코드>`와 그 연결. 국가·주·도 코드는 제보 값으로, 좌표는 주·도 대표 지점(없으면 수도, 그것도 없으면 0,0)으로 채워 둔다.
- 같은 주·도(주·도가 없으면 같은 국가)의 기존 장소 목록 `candidates`.
- 목록에 없는 게임·맵이면 새 게임·맵 자리(맵의 `era`는 비어 있음 → 채우기 전에는 `diff` 오류).
- 수정 제안의 `위치`는 국가·주·도 코드와 대표 지점 좌표를 바로 반영한다. 나머지 칸은 `todo`로 남긴다.
- 작업 목록에는 제보자 이름이 없다(출처 번호만). 공개 이미지 출처는 닉네임(`profiles.nickname`).

작업 목록 칸(`worklist.json` 항목):
- `touches` — 이 항목 때문에 바뀌는 행 키. 검수기가 이 목록으로 항목별로 묶는다. 행 키를 바꾸거나 행을 더하면 함께 고쳐야 하고, 빠지면 `diff`가 "작업 목록에 없는 변경"으로 경고한다.
- **같은 행 키를 여러 항목이 함께 가질 수 있다.** 그 행을 채택하면 그 행을 가진 모든 항목이 승인된다. 근거 출처의 `submission_id`는 그중 가장 먼저 접수된 제보.
- `new-` 로 시작하는 id는 임시다. 실제 id로 바꾸지 않으면 `diff` 오류. id가 쓰인 곳(장소 키, 맵 아래 연결 키, `touches`)을 모두 바꿔야 한다.
- `memo` — 판단 근거(검수기에 보인다). `reject_reason` — 전부 제외할 때 제보자에게 보일 사유 초안.
- `todo` — 남은 일. 비어 있지 않으면 `diff`가 경고한다(막지는 않음).

검수기와 반영:
- 탭 2에서 못 고치는 것(장소 id, 연결을 기존 장소로 옮기기, 행 추가, 별칭 글자)은 탭 1이나 `atlas.json`에서 고친 뒤 `diff`를 다시 만들고 검수기에서 "다시 읽기". 내용이 그대로인 항목만 결정을 이어받고, 바뀐 항목은 미결정으로 돌아간다.
- `apply`: 항목별로 하나라도 채택하면 승인, 전부 제외하면 반려(사유 필수). 그 사이 관리 화면에서 처리된 항목은 건너뛴다.

## 규칙

- 파일에서 빠진 행 = 삭제. 연결·근거 출처·별칭만 지울 수 있고, 게임·맵·장소 행은 지울 수 없다(diff에서 오류).
- 값 규칙: 근거 수준 공식·커뮤니티 추정·기타 / 시대 WWI·WWII·냉전·현대·근미래·기타 / 위치 범위 주·도·국가. 국가·주·도 이름은 Natural Earth 표준 한국어 이름(`public/geo`), 코드는 `adm0_a3`·`adm1_code`. 코드를 지어내지 않는다.
- 제보 이미지는 `submission:<비공개 경로>`로 들어 있고, 반영할 때 공개 버킷 `submissions/<제보 번호>/`로 복사된다(관리 화면 승인과 같은 경로, 탈퇴 익명화가 이 경로로 찾는다). 새 이미지 업로드는 관리 화면에서.
- 반영은 한 트랜잭션이다. DB 값이 diff 때와 다르면 전부 되돌리고 멈춘다 → `pull --force`부터 다시.
